# 证书吊销功能实现方案与密钥路径清单

更新日期：2026-11-13。本文已从初始研究稿更新为本次实际实现及后续讨论确认的规则。源码和接口说明对应当前工作区，设备上的实际路径、权限、构建参数和 TEE 存储后端仍需部署时核对；本次未连接或修改真实设备。

## 1. 本次实现范围

采用“离线 CA 登记吊销并导出 CRL → 上层分发 → 后端或部署工具验证并导入 → 应用接口重启 tems → TLS 握手执行吊销检查”的流程。设备不必定时连接 CA，也不在设备保存 CA 私钥。

| 模块 | 本次实现 |
|---|---|
| CA 工具 | 复用 `provisioning/ca.py` 已有 revoke、export_crl 及签发台账；未新增根 CA 对中间 CA 的吊销台账/导出向导 |
| 后端 CRL | 新增导入和查询接口；统一签名、发行方、有效期、编号及格式检查 |
| 证书查询 | `/api/security/certificates` 返回真实 revocationStatus、检查原因和待应用状态 |
| 应用接口 | 扩展原 `/api/cert/https/apply`，保持无请求体，按待应用变更操作 Nginx/tems |
| tems | Modbus TLS 主从双方在新握手时检查 CRL；通过重启读取新证书/CRL并断开旧连接 |
| 首次部署 | PC SSH 和本地工具增加 CRL 文件、发行方链及导入操作 |
| 日志 | 上传接收、校验失败、CRL 保存、TLS 拒绝、CRL 过期及服务操作等关键步骤记录日志，不记录私钥值 |

## 2. 配置项及默认目录

设备默认 INI 为 `/home/zlg/lc_data_set.ini`，后端和 tems 均通过 `LC_INI_PATH` 环境变量选择其他配置文件。需确保两者读取同一份配置。

```ini
[TLS]
ca_file = /etc/ems/pki/ca-roots.crt
# 可选，省略时自动取 ca_file 的完整路径加 .crls.pem
crl_file = /etc/ems/pki/ca-roots.crt.crls.pem
```

当前不使用初始研究稿中的 `crl_dir` 和 `revocation_policy`，无需添加这两项。`crl_file` 必须是与 ca_file 不同的绝对路径。更换配置路径需重启相应进程以重新读取配置。

设备私钥不是通过 `[TLS]` 中的上述两个字段配置的。HTTPS、Modbus 私钥的路径选择分别见下表；修改后端目录不会自动修改已编译的 tems 路径。

## 3. 密钥、证书与相关材料路径清单

本节按材料用途列出当前代码能够确认的全部主要密钥类别及关联文件。证书、CSR、公钥、CRL 和摘要不是秘密密钥，但需要受控管理其完整性。所有路径均不包含密钥值；变量目录和示例地址不代表真实生产配置。

### 3.1 设备 HTTPS 与 Modbus 身份

| 材料 | 默认设备位置 | 类型/读取方 | 路径覆盖方式及注意事项 |
|---|---|---|---|
| HTTPS 私钥 | `/etc/ssl/g3/g3.key` | RSA 私钥；Nginx、HTTPS 维护脚本 | 后端 SECURITY_CONFIG_FILE 指向的 JSON 可设置 HTTPS_CERT_DIR；脚本支持 `--dir`，enable_https.sh 使用 HTTPS_CERT_DIR 环境变量。应用接口会将后端目录传给脚本 |
| HTTPS 身份证书及中间链 | `/etc/ssl/g3/g3.crt` | 公开 fullchain；Nginx | 与 HTTPS 私钥共用目录；不含 CA 私钥 |
| HTTPS CSR | `/etc/ssl/g3/g3.csr` | 公开签发请求 | 同目录；设备保留私钥，将 CSR 交外部 CA |
| Modbus master 私钥（file 后端） | `/etc/ems/modbus/master.key` | RSA-3072 私钥；Modbus 主机 | Python 脚本使用 `--dir`，后端可配置 MODBUS_CERT_DIR；C 从 master.crt 路径同名替换扩展名得到 .key |
| Modbus slave 私钥（file 后端） | `/etc/ems/modbus/slave.key` | RSA-3072 私钥；Modbus 从机 | 同上；两个角色必须独立密钥 |
| Modbus master 证书及中间链 | `/etc/ems/modbus/master.crt` | 公开 fullchain，clientAuth | C 默认由 `MODBUS_TLS_CLIENT_CERT` 宏确定，非 INI 字段 |
| Modbus slave 证书及中间链 | `/etc/ems/modbus/slave.crt` | 公开 fullchain，serverAuth | C 默认由 `MODBUS_TLS_SERVER_CERT` 宏确定，非 INI 字段；验证实际 TCP 对端 IP SAN |
| Modbus CSR | `/etc/ems/modbus/master.csr`、`slave.csr` | 公开签发请求 | 同 Modbus 身份目录 |
| 共享 CA 根信任包 | `/etc/ems/pki/ca-roots.crt` | 公开信任锚；Python/tems 共用 | `[TLS] ca_file`；只接受经可信指纹核验的根，不保存根私钥 |
| CRL 持久包 | `/etc/ems/pki/ca-roots.crt.crls.pem` | 公开 CRL及辅助发行方证书；Python/tems | `[TLS] crl_file`；缺省为 ca_file 加 `.crls.pem`；辅助证书不提升为根信任 |

HTTPS 当前使用文件私钥，没有自动转入 TEE。`MODBUS_KEY_BACKEND=file|tee` 只选择 Modbus 密钥后端，不改变 HTTPS 私钥位置。file 后端私钥要求受控属主和 0600 权限；部署工具的公开证书导入、导出和中断恢复均不导出/替换私钥。普通续签复用原密钥；私钥泄露后必须换钥重新签发。

**自定义目录必须配套：** 后端 MODBUS_CERT_DIR、维护脚本 `--dir`、部署工具 `--modbus-dir` 及 tems 的证书编译路径须一致；HTTPS_CERT_DIR、部署工具 `--https-dir` 和实际 Nginx 配置也须一致。现有 HTTPS timer 默认目录另需按部署说明核对，不能只改某一个调用方。

源码依据：`exec/app/script/pki_common.py`、`modbus_certs.py`、`https_certificates.py`、`enable_https.sh`，`exec/app/script/security_config.py`，`logger/lib/modbus_transport.h`、`modbus_identity.c`。

### 3.3 管理电脑 CA 密钥和口令材料

`<CA目录>` 由 CA GUI 选择，或 CLI `--ca-dir` 指定，没有统一的生产绝对路径。`/secure/company-ca` 仅为既有说明示例，不代表实际目录。

| 材料 | 位置 | 说明 |
|---|---|---|
| 根 CA 私钥 | `<CA目录>/root-key.pem` | 口令加密 PKCS#8，默认 RSA-4096，用于建立签发 CA；只保留在受控 CA 管理电脑 |
| 签发 CA 私钥 | `<CA目录>/issuer-key.pem` | 口令加密 PKCS#8，默认 RSA-4096，签设备证书和 CRL |
| 根 CA 证书 | `<CA目录>/roots.pem` | 公开材料，设备通过根信任包导入 |
| 签发 CA 证书 | `<CA目录>/intermediates.pem` | 公开材料，随设备证书链及 CRL 辅助链分发 |
| 签发/吊销台账 | `<CA目录>/ledger.sqlite3` | 包含证书、吊销、CRL 编号和审计记录；不是私钥，但必须与 CA 数据整体受控备份 |
| CA 口令加密文件 | 用户选择的 `*.lcvault`，必须在 CA 目录之外 | 加密保存 CA 口令；独立保护口令不保存到文件旁，没有固定默认文件路径 |
| 口令文件派生加密密钥 | 无独立文件 | 由保护口令通过 scrypt 派生，用 AES-256-GCM 保护口令文件；不另建一份 .key 文件 |

CA 私钥、台账、口令文件及口令的备份/保管应遵循 provisioning/README.md。设备证书包不携带上述两份 CA 私钥。CRL 导出文件名由管理员选择，例如 issuer-crl.pem；导入设备后进入 3.1 中的持久包。

源码依据：`provisioning/ca.py`、`passwords.py`、`password_ui.py`。

## 4. CRL 校验及持久化

新增 `exec/app/script/crl_store.py`，由后端及部署工具复用；`pki_common.validate_identity()` 在配置了已存 CRL 时接入同样的吊销判断。普通证书路径验证继续使用 OpenSSL。

导入支持完整 PEM CRL 包或单份 DER CRL，可附公开发行方链。校验内容包括：

1. 大小、数量、格式及不支持的关键扩展；单字段/合并包上限 1 MiB。
2. issuer、AKI、签名、CA/cRLSign 权限及发行方可信链；签名哈希要求 SHA-256 或以上受支持算法。
3. thisUpdate/nextUpdate：拒绝未来发布、缺 nextUpdate 或时间区间错误；真实但已过期的 CRL 允许导入并标记 stale。
4. 按发行方密钥和身份范围保存最新 CRLNumber，拒绝低编号及同编号不同内容，允许同内容重试；不得移除既有永久吊销记录。
5. 证书按实际签发关系及序列号检查；同名但不同密钥的 CA 不得互相误吊销。

不支持 delta、间接、分区 CRL和临时挂起/恢复。有效名单即使包含本机身份，也应允许导入，不能为了维持旧身份而拒绝名单。

CRL 与编号保存在同一个原子替换 PEM 包内，采用文件锁、临时写入和 fsync，避免分别更新文件与编号产生不一致。操作锁串行化服务应用与导入；标记先于文件替换，异常中断最多导致额外一次待应用，不应漏记更新。该机制不等于抵御拥有系统权限的删除或整盘回滚，也不宣称具有 TEE 防回滚能力。

## 5. TLS 与过期行为

| 情况 | 当前行为 |
|---|---|
| 从未导入 CRL/文件不存在 | 兼容旧设备，保留既有链/用途/时间等检查，查询 unavailable；不宣称已执行吊销检查 |
| 已有 CRL 包但缺叶证书发行方名单 | 查询 unknown；Modbus TLS 和身份校验拒绝 |
| 有效名单列出证书 | 拒绝新连接及使用该身份 |
| CRL 过期且列出证书 | 继续拒绝该身份，查询仍为 revoked |
| CRL 过期且未列出证书 | 允许连接，查询 stale；其他证书验证仍执行 |
| 提供了上级 CA 的 CRL | 同时检查对应中间 CA 的吊销 |
| 缺少上级 CA 的 CRL | 本版不强制要求；不声称全链 CRL 已完整覆盖 |
| 根信任锚撤信 | 通过受控根包更新移除/替换，非依赖根自签 CRL |

`logger/lib/modbus_transport.c` 加载 CRL 到 X509_STORE，启用 CRL_CHECK/CRL_CHECK_ALL；回调只按上述规则允许 CRL 过期以及缺少非叶级 CRL，不放行签名错误、证书过期、证书吊销等其他失败。主机继续验证从机 IP SAN，从机继续要求主机客户端证书，角色 EKU 和私钥匹配规则保持。

CRL 更新通过重启 tems 生效，关闭旧连接后再按新名单握手；没有实现热重载上下文、逐连接后台重验或“更新后 5 秒内”运行时回执。名单到期不会自动断开旧连接，后续新握手按上述过期规则处理。会话缓存和 ticket 继续保持关闭。

HTTPS 本地导入/检查/应用使用 CRL；浏览器或其他 HTTPS 客户端是否拒绝被吊销的服务端身份，仍依赖客户端策略。Nginx ssl_crl 面向客户端证书校验，本版未改变 Web Bearer 认证，也未开启 Web mTLS。旧明文/白名单入口不在 TLS 吊销覆盖范围。

## 6. 接口、服务应用与状态

| 方法与路径 | 当前职责 |
|---|---|
| GET `/api/cert/crls` | 查询发行方、编号、发布时间、到期时间、吊销数量、状态及 pending 服务 |
| POST `/api/cert/crls/import` | FormData file（CRL）和可选 chain（发行方链）；验证并保存，不自动重启 |

| POST `/api/security/certificates/verify` | 复用现有身份校验并反馈吊销状态 |

| CRL | 无操作 | restart |
| 无变更 | 无操作 | 无操作 |

多项变更合并，每个服务操作一次。按服务命令成功及 tems active 检查判定应用成功，不采集运行时批次。返回 data.changed/applied/services/pending；部分失败为 HTTP 503 / CERTIFICATE_APPLY_FAILED，保留失败项供重试，成功项清除标记。后端与 tems 属于独立服务，重启 tems 不会连带终止后端。

待应用标记位于 ca_file 所在目录：`.nginx-apply-required`、`.tems-apply-required`；原 HTTPS `.reload-required` 仍兼容。这些标记不是密钥。服务权限由部署授予，后端不自动 sudo。

证书清单 revocationStatus：good（有效对应名单未列出）、revoked（确认吊销）、stale（对应名单过期且未确认吊销）、unknown（缺对应名单）、unavailable（未导入或检查失败）、not_applicable（根信任锚）。附 revocationReason、revocationCheckedAt，匹配名单时带 crlNumber/crlNextUpdate；applyPending 仅表示相应服务尚待应用。chainVerified、validityStatus 和 privateKeyVerified 仍独立，确认吊销时整体 status 为 invalid。

## 7. 部署流程

1. 保持三种设备身份私钥独立，生成 CSR，交受控 CA 签发。
2. 通过独立可信渠道核对根指纹，导入根和对应身份证书。
3. CA 导出 CRL；初始无吊销记录可使用空名单。首次导入签发 CA CRL 时附签发 CA 中间链；直接由可信根签发可省略。
4. PC 部署 GUI/CLI、本地工具或后端接口导入 CRL。
5. 上层调用统一应用接口，或使用部署工具应用；查询服务结果、pending 和证书状态。
6. 密钥泄露时立即发布并分发 CRL，安排新角色密钥及证书；不能仅复用泄露密钥续签。

部署工具新增命令：`crl-import --file FILE [--chain FILE]`。证书首次部署保持原有整包检查与应用流程；仅 CRL 待应用时只重启 tems，避免因本机新近被吊销而跳过必要重启。PC GUI 保留/复用 SSH 连接，并提供“断开 SSH 连接”按钮；操作完成后可主动断开，关闭窗口或清除口令时释放连接，部署进行中需等待完成再断开。CLI 仍为每条命令结束后断开。

更新设备需匹配的 app/script 和重新构建后的 tems，配置相同 LC_INI_PATH、密钥后端及证书路径。启用 CRL 的维护 Python 需具备 cryptography，建议使用后端 requirements-security.txt 的 >=42.0.8。上层负责在 CRL 到期前更新，并把名单送到所有相关验证方；只更新被吊销设备自身不够。

## 8. 验证与交付边界
