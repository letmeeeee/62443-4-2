# LC400 前端联调修改反馈（2026-11-13）

本次调整涉及 CRL 导入/查询、证书吊销状态及证书变更统一应用。本文依据当前后端路由、权限钩子和统一响应处理编写，供前端调整页面调用。JSON 为结构示例，不是生产设备抓包；实际时间、数量、原因和服务执行结果以接口为准。

2026-11-11 反馈中“revocationStatus 固定为 unavailable、尚未接入 CRL”的说明已被本次实现替代。涉及本次改动的调用规则以本文为准。后端代码和本地测试已完成，目标设备及页面端联调仍需验证。

## 一、接口变更清单

| 方法 | 接口 | 变化 | 前端调整 |
|---|---|---|---|
| GET | `/api/cert/crls` | 新增 CRL 清单和待应用服务查询 | 增加 CRL 表格、有效期状态和待应用提示 |
| POST | `/api/cert/crls/import` | 新增 CRL 导入 | 新增上传 CRL 和可选发行方证书链的操作 |
| POST | `/api/cert/https/apply` | 从仅应用 HTTPS 扩展为应用全部待生效证书/CRL变更 | 原请求参数保持；按钮改名为“应用证书变更”，展示实际服务结果 |
| GET | `/api/security/certificates` | revocationStatus 返回真实结果，新增原因、时间及 applyPending | 更新吊销状态和待应用展示 |
| GET | `/api/security/status` | checks.certificates.data 共用新的证书条目 | 同步更新安全总览中的证书组件 |
| GET | `/api/security/config-summary` | certificates 共用新的证书条目 | 同步更新配置摘要展示和导出 |
| GET | `/api/cert/check?role=master\|slave` | 原校验接入 CRL，revocation_status 不再固定 | 保持参数和响应层级，注意此处为下划线字段 |
| POST | `/api/security/certificates/verify` | 校验接入 CRL，成功响应提供真实吊销结果 | 保持 JSON role 参数；失败后从清单查询具体状态 |
| POST | `/api/cert/identity/import`、`/api/security/certificates/import`、`/api/cert/https/identity/import` | 参数不变，导入检查增加 CRL | 保留上传流程；处理新增可能的校验失败，不把导入成功展示为已应用 |
| POST | `/api/cert/ca/import` | 参数不变，成功后记录 Nginx 和 tems 待应用 | 导入后提示应用证书变更 |

管理类 `/api/cert/*`、`/api/security/certificates*` 按当前权限映射要求管理员（角色 4）。安全总览/配置摘要沿用 security:read（角色 3/4）。这是当前权限规则，不能按旧反馈将直接证书管理接口开放给角色 3。

GET 携带 `Authorization: Bearer <token>`。POST 额外携带 `X-CSRF-Token`；沿用项目已有同源策略。FormData 上传不手动设置 Content-Type，让浏览器生成 multipart boundary。不要把 Token 放入 URL。

## 二、新增 CRL 查询

```http
GET /api/cert/crls
Authorization: Bearer <token>
```

成功 HTTP 200，沿用证书模块的 `status/message/data` 包装；成功不保证有顶层 `ok`：

```json
{
  "status": 3,
  "message": "Certificate revocation lists",
  "data": {
    "crls": [
      {
        "issuer": "CN=Example Issuing CA",
        "issuerKeyId": "0123456789abcdef0123456789abcdef01234567",
        "crlNumber": "12",
        "thisUpdate": "2026-11-13T02:00:00+00:00",
        "nextUpdate": "2026-11-20T02:00:00+00:00",
        "status": "valid",
        "reason": null,
        "revokedCount": 2
      }
    ],
    "pending": ["tems"]
  }
}
```

| 字段 | 类型/含义 | 展示要求 |
|---|---|---|
| crls | 数组，可为空 | 空数组显示“未导入 CRL”，不能当成已检查且无人吊销 |
| issuer / issuerKeyId | 发行方名称/密钥标识 | 同名 CA 可能使用不同密钥，不能只按 issuer 合并列表 |
| crlNumber | 十进制字符串 | 直接作为字符串显示，不转 Number，避免大整数精度丢失 |
| thisUpdate / nextUpdate | ISO 8601 时间 | 分别为发布时间、下次更新时间/到期时间，按统一时区显示 |
| status | valid / stale / invalid | 分别显示“有效”“CRL 已过期”“CRL 校验失败”；未知值保留兜底 |
| reason | null 或诊断说明 | 无需依赖固定中文文本进行业务判断 |
| revokedCount | 数字 | 吊销条目数，不是设备在线数或连接数 |
| pending | nginx/tems 字符串数组 | 全部证书/CA/CRL变更的待应用服务，不只属于当前选中 CRL |

当前没有删除 CRL、下载 CRL、单独的预检或 CRL 专用应用接口，页面不要调用这些未实现路径。

## 三、新增 CRL 导入

```http
POST /api/cert/crls/import
Authorization: Bearer <token>
X-CSRF-Token: <csrf_token>
Content-Type: multipart/form-data; boundary=...
```

| FormData 字段 | 必填 | 内容 |
|---|---|---|
| file | 是 | 完整 PEM CRL 包或单份 DER CRL |
| chain | 否 | PEM 发行方证书链；签发 CA 的 CRL 首次导入通常需要提供中间链，根直接签发可省略；后续可复用已保存链 |

字段每项不得超过 1 MiB，文件非空；合并后的持久包也有限制，最终以服务端验证为准。文件选择不要只限定一种扩展名，PEM/DER 由内容识别；不上传私钥或 CA 口令。

调用示意：

```javascript
const form = new FormData();
form.append('file', crlFile);
if (issuerChainFile) form.append('chain', issuerChainFile);

const response = await fetch('/api/cert/crls/import', {
  method: 'POST',
  headers: {
    Authorization: `Bearer ${token}`,
    'X-CSRF-Token': csrfToken,
  },
  body: form,
});
const body = await response.json();
// 先按 HTTP 状态处理，再读各接口对应的包装结构。
```

成功 HTTP 200，结果在 data：

```json
{
  "status": 3,
  "message": "CRLs imported; apply to restart Modbus",
  "data": {
    "imported": true,
    "restart_required": true,
    "crls": [
      {
        "issuer": "CN=Example Issuing CA",
        "issuerKeyId": "0123456789abcdef0123456789abcdef01234567",
        "crlNumber": "12",
        "thisUpdate": "2026-11-13T02:00:00+00:00",
        "nextUpdate": "2026-11-20T02:00:00+00:00",
        "status": "valid",
        "reason": null,
        "revokedCount": 2
      }
    ],
    "pending": ["tems"]
  }
}
```

crls 为导入后的名单，结构同查询接口。前端提示“CRL 已导入，待应用”，刷新 CRL 和证书清单，并显示应用入口。

导入成功不自动重启服务。相同名单可重试；编号回退、同编号不同内容、验签失败、不可信发行方、未来发布时间、不支持的 delta/间接/分区 CRL 等会拒绝。**真实但已过期的 CRL 可以导入**，应提示“CRL 已过期”，不能强行把此情况转成上传失败。有效名单即使吊销了本机身份也可导入，前端需据返回的证书状态提示维护。

CRL 的登记吊销在 CA 管理工具执行，设备 Web 页面仅导入 CA 已签名的名单，不新增“输入序列号即可签发吊销”的设备接口。

## 四、统一应用接口：请求保持不变，行为扩大

```http
POST /api/cert/https/apply
Authorization: Bearer <token>
X-CSRF-Token: <csrf_token>
```

无请求体，不传 role、service、证书路径或 CRL 路径。后端根据持久待应用标记执行所有相关操作，不支持前端指定只应用某一张证书。

| 已导入的变更 | 实际动作 |
|---|---|
| HTTPS 身份证书 | Nginx 按需重载，未运行则启动 |
| Modbus master/slave 身份证书 | 重启 tems.service |
| 共享 CA 根证书 | Nginx 重载/启动 + tems 重启 |
| CRL | tems 重启 |
| 无变更 | 无服务操作 |

前端按钮名称改为“应用证书变更”。操作前说明可能中断 Modbus 连接；同一次导入流程可先完成多份材料，再统一应用。不要每次上传后自动无提示触发重启。

成功 HTTP 200 示例：

```json
{
  "status": 3,
  "message": "Certificate changes applied",
  "data": {
    "changed": true,
    "applied": true,
    "services": {
      "nginx": {"action": "reload-or-start", "status": "success"},
      "tems": {"action": "restart", "status": "success"}
    },
    "pending": []
  }
}
```

services 仅包含本次操作的服务，可能只有 nginx 或 tems。Nginx 的 action 是 reload-or-start，不能据此展示为一定发生了完整重启。无变更时 changed:false、applied:true、services:{}、pending:[]，显示“无需应用”，不显示“已重启服务”。

应用成功以服务命令结果及 tems active 为准，不返回 storedGeneration/runtimeGeneration/effectiveAt 等运行时回执。应用后重新查询 pending 和证书状态。

### 4.1 部分失败与超时处理——必须按实际统一错误响应处理

生产 main.py 注册了统一错误归一化。路由内部虽然生成了部分失败的 services/pending，**HTTP >=400 时该 data 会被移除**。线上应用失败响应形如：

```json
{
  "ok": false,
  "code": "CERTIFICATE_APPLY_FAILED",
  "trace_id": "<追踪标识>",
  "message": "Service temporarily unavailable"
}
```

因此 HTTP 503 后不能读取 error.response.data.data.services，也不能假设两个服务都失败或都没执行。前端处理顺序：

1. 显示“部分或全部证书变更应用失败，请检查待应用状态”，保留 trace_id 便于排查。
2. 重新 GET `/api/cert/crls` 获取 data.pending；刷新证书清单获取 applyPending。
3. 仍有 pending 时保留重试入口；后端正常应用路径只处理尚待应用的服务。
4. 对网络错误、浏览器超时或反向代理错误也先查询状态，不自动连续重试写操作。pending 是待应用状态，不是新增加的运行时批次证明。

应用涉及串行服务操作，可能持续数分钟。该请求使用单独的较长超时配置（按实机时延及网关限制设置，例如 6–10 分钟），并禁止重复点击；超时不等于后端停止执行。前端可显示“正在应用证书变更”，避免同时高频刷新耗时的证书自检接口。

## 五、证书条目新增/变化字段

以下三个位置共用条目模型：

| 接口 | 数组位置 |
|---|---|
| GET `/api/security/certificates` | data |
| GET `/api/security/status` | checks.certificates.data，先判断 available |
| GET `/api/security/config-summary` | certificates |

条目示例（节选）：

```json
{
  "role": "master",
  "status": "valid",
  "validityStatus": "valid",
  "chainVerified": true,
  "privateKeyVerified": true,
  "privateKeyCheckReason": "VERIFIED",
  "revocationStatus": "stale",
  "revocationReason": "CRL_EXPIRED",
  "revocationCheckedAt": "2026-11-13T02:00:00+00:00",
  "crlNumber": "12",
  "crlNextUpdate": "2026-11-12T02:00:00+00:00",
  "applyPending": true
}
```

| revocationStatus | 建议展示 | 当前执行含义 |
|---|---|---|
| good | 当前 CRL 未列入吊销 | 有有效对应名单，尚未列出该身份；不代表其他维度均通过 |
| revoked | 已吊销 | 拒绝该身份；过期 CRL 已列出的身份仍为 revoked |
| stale | CRL 已过期 | 旧名单未列出该身份时允许握手；证书自身有效期/链等仍检查 |
| unknown | 缺少对应发行方 CRL | 已有 CRL 包但叶证书发行方覆盖缺失，校验/TLS 拒绝 |
| unavailable | 吊销状态不可用 | 尚未导入或检查失败，结合原因显示；不等于未吊销 |
| not_applicable | 不适用 | 根信任锚，通过根信任包管理 |

当前 revocationReason 包括 CRL_NOT_CONFIGURED、CRL_CHECKED、CRL_EXPIRED、CERTIFICATE_REVOKED、ISSUER_CRL_MISSING、CRL_CHECK_FAILED、TRUST_ANCHOR；校验接口还可能出现 CERTIFICATE_UNAVAILABLE。保留未知原因码兜底，不将 reason 文本用于权限或状态判断。

字段兼容要求：

- revocationCheckedAt、crlNumber、crlNextUpdate 不是所有条目都必有；根条目、无法解析条目或检查失败可能缺少这些字段。缺字段显示“—/未知”，不能默认 good。
- revoked 时整体 status 改为 invalid；chainVerified、validityStatus、privateKeyVerified 仍分别表达自己的维度，可以同时为 true/valid。
- stale、unknown、unavailable 不一定改变整体 status 或 errorCount；前端需要独立展示吊销状态，不能只看汇总数字。
- CRL 本身的 status:valid/stale/invalid 与证书的 revocationStatus 是不同枚举，不混用 expired/stale。
- applyPending 表示角色对应的服务待应用，不是单张证书的修改记录。例如 master 更新导致 tems 待重启，slave 也可能显示 applyPending:true；根条目在任一相关服务待应用时为 true。
- 查询的是磁盘上最新材料。导入后即使显示 revoked，只要 applyPending 仍在，就不能说旧 Modbus 连接已经被阻断。
- 不删除/改名既有 chainVerified、validityStatus、privateKeyVerified 等字段，页面将各维度分开展示。

## 六、现有校验、导入接口兼容

`GET /api/cert/check?role=master` 请求不变；成功使用 data 包装：

```json
{
  "status": 3,
  "message": "CA chain, role and private key verified",
  "data": {"role": "master", "valid": true, "chain_verified": true, "revocation_status": "stale"}
}
```

`POST /api/security/certificates/verify` 请求仍为 `{"role":"master"}` 或 slave。成功使用顶层字段：

```json
{
  "ok": true,
  "valid": true,
  "role": "master",
  "revocationStatus": "good",
  "revocationReason": "CRL_CHECKED",
  "revocationCheckedAt": "2026-11-13T02:00:00+00:00",
  "crlNumber": "12",
  "crlNextUpdate": "2026-11-20T02:00:00+00:00"
}
```

校验失败通常返回 422；统一错误处理会移除 valid/revocationStatus 等路由内部字段，需刷新证书清单查看细节，不能按成功结构解析失败响应。

Modbus/HTTPS 身份导入字段、共享 CA 导入的 fingerprint 等参数不变；成功仍可能返回 restart_required:true 或 reload_required:true。前端将其解释为“待应用”，然后使用统一应用入口。已配置 CRL 后，被吊销证书或缺少对应发行方名单的身份导入/检查可能失败；过期名单不因过期本身拒绝未列名身份。

## 七、错误、页面交互与验收

| 情况 | 前端处理 |
|---|---|
| 400 / PKI_INVALID_REQUEST 等 | 提示文件/字段错误，修正后再提交 |
| 401 / SESSION_INVALID | 沿用会话失效处理 |
| 403 / 权限、CSRF、会话锁定等原因 | 按 code 使用既有处理；不一律归为账号权限不足 |
| 422 / PKI_VALIDATION_FAILED、CERTIFICATE_INVALID 等 | 提示验证失败，保留原列表；错误消息可能仅为原因码，使用 trace_id 排查 |
| 503 / CERTIFICATE_APPLY_FAILED | 依第 4.1 节重新查询 pending，再展示待重试状态 |
| 503 / PKI_UNAVAILABLE 等 | 提示服务不可用；不能当成导入成功 |
| 未知错误码或非 JSON 响应 | 通用错误兜底；写操作结果不明时先查状态 |

页面建议：证书管理增加“CRL 管理”区域，展示发行方、编号、发布时间、到期时间、吊销数量、名单状态；提供导入按钮和统一应用按钮。CRL 选择器附可选发行方链字段；导入、应用期间禁用重复提交。网络恢复后按既有登录态重新查询，不以本地缓存判断应用成功。

联调至少验证：

1. 未导入名单：CRL 空列表、证书 unavailable，不展示“未吊销”。
2. 正常导入：显示编号/有效期和 tems 待应用；导入本身不显示重启成功。
3. 过期名单：导入成功，显示 stale；旧名单中已吊销身份仍显示 revoked。
4. 伪造/错误发行方/旧编号：导入失败，旧列表保留。
5. HTTPS、Modbus、共享 CA、CRL分别导入后，应用操作匹配对应服务；多项更新合并。
6. 无变更：显示“无需应用”；部分失败：503 后重新查询 pending，只提示仍待应用项。
7. 证书私钥自检通过但已吊销：两个维度分别展示；三个返回证书数组的页面同步。
8. 低权限、会话失效、CSRF 缺失、应用超时和网关非 JSON错误均有明确处理。

PC 部署工具新增的“断开 SSH 连接”按钮属于独立桌面 GUI，不是新增 Web HTTP 接口；本次无需在 Web 页面增加 SSH 断开调用。CRL 存储路径属于后端部署配置，上传请求不传文件系统路径。
