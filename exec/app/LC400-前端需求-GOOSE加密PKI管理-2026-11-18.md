# LC400 前端需求：GOOSE 加密通信 PKI 管理

日期：2026-11-18  
适用版本：已新增 `/api/cert/goose/` 接口的后端版本。  
对接依据：`routes/route_cert.py`、`script/goose_pki.py`，以下路径、字段和示例均按当前实现整理。

## 1. 目标与范围

在现有 PKI 管理页面增加独立的 **GOOSE PKI 管理**入口，支持上传本端证书、本端私钥、
CA 信任根、CRL，查询当前安装材料和待应用批次，并执行“校验并应用”或“重试应用”。

复用现有 TLS 页面的布局、文件选择、认证和错误提示组件；GOOSE 的材料、批次、接口
与 TLS 分开，不能混用 TLS master/slave/HTTPS 的批次或共享 CA/CRL 接口。
现有 TLS 和其他页面行为保持不变。

GOOSE 当前采用外部四文件导入流程，**不传 `pki_mode`、不传 `role`**，也不随 TLS
`general` / `trina` 页面模式切换为 CSR 流程。该入口不需要调用尚未实现的设备模式配置接口。

## 2. 页面需求

### 2.1 当前材料区域

进入页面调用 `GET /api/cert/goose/status`，展示以下内容：

| 项目 | 数据来源 | 展示要求 |
| --- | --- | --- |
| 安装状态 | `data.installed` | false 显示“尚未安装 GOOSE PKI”；true 显示“已安装 GOOSE PKI” |
| 当前材料代次 | `data.generation` | 可复制的标识，用于与批次关联；不要求用户理解文件目录 |
| 本端证书 SHA-256 | `data.sha256` | 可分组显示和复制，不能显示成 AES 会话密钥指纹 |
| CRL 列表 | `data.crls` | 展示颁发者、CRL 编号、更新时间、下次更新时间、吊销条目数和状态 |
| 刷新按钮 | 再次 GET | 刷新失败保留上次信息并标记“查询失败/信息可能已过时” |

**状态语义：** `installed=true` 只表示已有一套材料安装在设备上，不代表进程重启成功、
当前 GOOSE 握手成功或业务通信正常。接口不返回实时服务状态、握手状态、收包计数、
证书 CN/有效期、CA 详情或私钥详情；页面不能据此显示“GOOSE 通信正常”或虚构这些字段。
批次 `applied` 是上次应用动作成功的记录，也不是持续运行健康检查。

### 2.2 四类上传材料

| 页面名称 | `part` | 支持内容 | 说明 |
| --- | --- | --- | --- |
| 本端证书 | `identity` | PEM 证书，叶证书在前，可紧随中间 CA 链 | 身份公钥须为 EC P-256，与本端私钥匹配；不要求文件名固定 |
| 本端私钥 | `key` | 单个未加密 PEM 私钥，PKCS#8 或 EC PRIVATE KEY | 仅支持 EC P-256（prime256v1），不支持 RSA、带密码私钥或自定义 PBKDF2 信封 |
| CA 信任根证书 | `ca` | PEM 自签名根证书，可含多个根 | 不是 CA 私钥；中间 CA 不放在此处作为信任根 |
| CRL | `crl` | PEM 或 DER CRL；PEM 包可附颁发者证书 | 签名、有效期、CRL 编号及回退限制由后端校验 |

通用规则：

- 每次上传一个文件，大小为 **1～1,048,576 字节（1 MiB，含上限）**。
- 文件选择器可提示 `.pem/.crt/.cer/.key/.crl` 等后缀，但不能只按后缀判断真实格式；
  证书和 CA 即使后缀为 `.cer` 也必须是 PEM 内容。
- 不需要上传对端证书 `peer.crt`；不需要输入对端指纹、CA 私钥、私钥密码或服务器路径。
- 没有独立 `chain/import` 接口。中间链放入本端证书 PEM 文件，颁发者证书也可随 CRL PEM 包提供。
- 不显示 CSR 生成、私钥导出、清空 CRL、重置为明文或删除当前配置的按钮。
- 上传成功只表示“已暂存”，不表示四项材料相互匹配或已经生效；完整校验在 apply 执行。
- 私钥不预览、不回显、不写控制台、埋点、错误上报或浏览器持久存储。请求拦截器不得记录文件正文。

### 2.3 批次与操作区域

显示本批次编号、后端状态、本批次已上传项目、上传进度，以及“校验并应用/重试应用/刷新状态”按钮。

| 后端状态 | 页面文案 | 允许操作 |
| --- | --- | --- |
| `staged` | 材料已暂存，尚未应用 | 上传/替换本批次材料，校验并应用 |
| `installed` | 文件已安装，服务应用待完成 | 重试应用同一批次、刷新；禁止再上传到该批次 |
| `applied` | 本批次应用成功 | 刷新状态；后续修改需创建新批次 |
| 请求结果未知 | 结果待确认 | 保留原编号，查询原批次；禁止自动重新上传或新建批次 |

`parts` 表示**本批次实际上传过的材料**，不包含从当前安装版本继承的项目，不能直接将
“parts 没有四项”解释为材料缺失。

首次安装时前端引导上传全部四项；已有配置时允许只上传变更项，后端会在新批次建立时
快照继承当前四项。最终是否完整、匹配、有效，以 apply 的校验结果为准。

## 3. 认证及响应通用约定

所有接口要求登录且具备当前后端配置的管理员权限，复用已有权限能力判断，不在新页面
硬编码新的管理员数字。前端可以隐藏无权操作入口，最终权限仍以后端为准。

```http
Authorization: Bearer <session_token>
X-CSRF-Token: <csrf_token>
```

所有请求带 `Authorization`，POST 统一带 `X-CSRF-Token`，令牌来自现有登录流程。
不要把 session_token 放入 URL。沿用现有请求组件的其他必要公共请求头。

- 文件上传：`multipart/form-data`，浏览器使用 `FormData`，**不要手动写 Content-Type**，避免丢失 boundary。
- apply：`application/json`。
- 成功：HTTP 200，业务 `status=3`；成功响应**没有 `ok:true` 字段**。
- PKI 业务错误通常包含 `ok:false`、`status:-1`、`code`、`message`。
- 公共认证/CSRF/限流错误的结构可能不同，可能只有 `error` 或 `code`，不能强制要求每个错误都含 `status/message`。
- 以 HTTP 状态码和 `code` 分支处理，不通过匹配英文 `message` 判断业务状态。

## 4. 接口清单

以下共 7 个实际调用路径，基地址使用现有后端 API 地址。

| 方法 | 完整路径 | 用途 |
| --- | --- | --- |
| POST | `/api/cert/goose/identity/import` | 暂存本端证书及其可选中间链 |
| POST | `/api/cert/goose/key/import` | 暂存本端 EC P-256 私钥 |
| POST | `/api/cert/goose/ca/import` | 暂存 CA 信任根证书 |
| POST | `/api/cert/goose/crl/import` | 暂存 CRL |
| GET | `/api/cert/goose/status` | 查询当前已安装材料 |
| GET | `/api/cert/goose/status?batch_id={batch_id}` | 查询指定批次 |
| POST | `/api/cert/goose/apply` | 校验、安装材料并应用 GOOSE 服务 |

### 4.1 四个文件上传接口

四个路径共用参数格式：

| 字段 | 位置 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- | --- |
| `file` | multipart | File | 是 | 对应类型的单个文件 |
| `batch_id` | multipart | string | 首次否，后续是 | 省略或空值会创建新批次；后续必须传首次返回的标识 |

**四项必须串行上传。** 首次上传拿到 `batch_id` 后，后续请求复用同一编号。
首次同时上传四个文件但均不带 batch_id，会产生四个独立批次，不能组合应用。
四种材料没有固定的上传先后顺序。

首次上传本端证书的成功响应示例：

```json
{
  "status": 3,
  "message": "GOOSE PKI material staged; apply batch to activate",
  "data": {
    "batch_id": "1234567890abcdef1234567890abcdef",
    "status": "staged",
    "parts": ["identity"]
  }
}
```

该批次四项上传完成后，`data.parts` 为 `["ca", "crl", "identity", "key"]`。
`parts` 是字符串数组，顺序不作为前端业务依据；`pending` 在 staged 时可以不存在。

### 4.2 查询当前安装材料

```http
GET /api/cert/goose/status
```

尚未安装时：

```json
{
  "status": 3,
  "message": "GOOSE PKI status",
  "data": { "installed": false }
}
```

已安装时，以下证书指纹、颁发者和时间仅为格式示例：

```json
{
  "status": 3,
  "message": "GOOSE PKI status",
  "data": {
    "installed": true,
    "generation": "1234567890abcdef1234567890abcdef",
    "sha256": "A1A1A1A1A1A1A1A1A1A1A1A1A1A1A1A1A1A1A1A1A1A1A1A1A1A1A1A1A1A1A1A1",
    "crls": [
      {
        "issuer": "CN=Example Root CA",
        "issuerKeyId": "00112233445566778899aabbccddeeff00112233",
        "crlNumber": "2",
        "thisUpdate": "2026-11-16T00:00:00+00:00",
        "nextUpdate": "2026-11-23T00:00:00+00:00",
        "status": "valid",
        "reason": null,
        "revokedCount": 0
      }
    ]
  }
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `installed` | boolean | 是否存在当前安装材料 |
| `generation` | string，可缺省 | 当前材料代次，与安装它的 batch_id 对应 |
| `sha256` | string，可缺省 | 本端叶证书 SHA-256，64 位十六进制 |
| `crls` | array，可缺省 | CRL 公开清单，可能有多个颁发者 |
| `crls[].crlNumber` | string | 保留为字符串，不能强制转换为 JS Number，避免大整数精度丢失 |
| `crls[].status` | string | `valid` 正常、`stale` 已过期、`invalid` 校验异常 |
| `crls[].reason` | string/null | 校验异常原因；仅作说明，不作为稳定枚举解析 |
| `crls[].thisUpdate/nextUpdate` | ISO 8601 string | 按明确时区展示，可转换为设备/用户使用的时区 |
| `crls[].revokedCount` | number | CRL 中吊销条目数 |

可使用返回的 `generation` 再查询对应批次，补充其历史应用结果。当前安装查询本身没有
`pending` 或服务运行状态。CRL 过期/异常应明确提示，不能因为 `installed=true` 显示全绿。

### 4.3 查询指定批次

```http
GET /api/cert/goose/status?batch_id=1234567890abcdef1234567890abcdef
```

```json
{
  "status": 3,
  "message": "GOOSE PKI status",
  "data": {
    "batch_id": "1234567890abcdef1234567890abcdef",
    "status": "staged",
    "parts": ["ca", "crl", "identity", "key"]
  }
}
```

`batch_id` 当前是 32 位小写十六进制标识，前端按不透明字符串保存、原样传回。
批次查询不返回文件正文、私钥摘要、文件名或每项材料的详细检查结果。
不存在或非法批次当前可能返回 **422 `PKI_VALIDATION_FAILED`**，不是约定为 404。

### 4.4 校验并应用

```http
POST /api/cert/goose/apply
Content-Type: application/json
```

```json
{ "batch_id": "1234567890abcdef1234567890abcdef" }
```

后端同步完成四项匹配/证书链/CRL 校验，原子安装材料，并重启、检查 GOOSE 服务。
这不是异步任务接口，没有任务 ID、百分比进度或独立启动任务的调用。

应用成功：HTTP 200。

```json
{
  "status": 3,
  "message": "GOOSE PKI batch applied",
  "data": {
    "batch_id": "1234567890abcdef1234567890abcdef",
    "status": "applied",
    "parts": ["ca", "crl", "identity", "key"],
    "pending": []
  }
}
```

材料已经安装，但服务应用失败：HTTP 503。

```json
{
  "ok": false,
  "status": -1,
  "code": "GOOSE_PKI_APPLY_FAILED",
  "message": "Files installed; GOOSE service application failed; retry this batch",
  "data": {
    "batch_id": "1234567890abcdef1234567890abcdef",
    "status": "installed",
    "parts": ["ca", "crl", "identity", "key"],
    "pending": ["goose"]
  }
}
```

此时显示：“GOOSE PKI 文件已安装，服务应用未完成，请重试应用。”重试仍调用同一路径，
携带同一个 batch_id。不能自动重新上传文件、重新创建批次或调用 TLS apply。

应用成功后，刷新“当前安装材料”和“本批次状态”。成功文案为“GOOSE PKI 应用成功”，
不要显示“EMS 已连接”或“加密通信正常”。应用会重启 GOOSE 服务，操作前提示短暂中断
GOOSE 接收，并允许用户取消；只在用户点击并确认后提交。

## 5. 错误码与前端处理

| HTTP | code / 情况 | 前端处理 |
| --- | --- | --- |
| 400 | `PKI_INVALID_REQUEST` | 请求格式、文件大小、part 或 JSON 不合法；提示检查，不自动重试 |
| 401 | `SESSION_INVALID` | 按现有登录失效流程处理，保留可恢复的批次编号 |
| 403 | `FORBIDDEN` | 非管理员权限；禁用写操作并提示权限不足 |
| 403 | 公共 CSRF 校验失败或 `SESSION_LOCKED` | 按现有认证组件解锁/恢复；不能统一解释为证书错误 |
| 409 | `PKI_BATCH_CONFLICT` | 批次不可修改、已被替换，或其基础配置已变化；刷新状态，用户决定是否新建批次 |
| 422 | `PKI_VALIDATION_FAILED` | 格式/算法/证书链/匹配/CRL/批次校验失败；提示检查材料并联系后台查看审计 |
| 503 | `GOOSE_PKI_APPLY_FAILED` | 根据响应 data 显示 installed/pending，保留原编号并提供重试应用 |
| 503 | `PKI_UNAVAILABLE` 或其他服务不可用 | 状态可能未确定；查询原批次，不能直接断言文件未安装 |
| 429 | `RATE_LIMITED` | 提示请求频繁，停止密集重试 |
| 超时/断网/代理错误/5xx | 响应缺失或非 JSON | 保留原编号，显示“结果待确认”；恢复后查询原批次与当前材料 |

错误响应示例：

```json
{
  "ok": false,
  "status": -1,
  "code": "PKI_VALIDATION_FAILED",
  "message": "certificate or CSR validation failed; see server audit"
}
```

当前后端复用 PKI 通用错误文案，其中可能出现 “CSR” 或 “Custom PKI”。GOOSE 页面可按
code 映射中文提示，不应因此跳转 CSR 流程。422 不保证返回具体失败文件、校验明细或
字段级错误，前端不要依赖未实现的数据结构。

## 6. 调用流程与交互细节

### 6.1 首次安装

1. 进入页面查询当前状态，显示尚未安装。
2. 用户选择四类文件，前端检查空文件及 1 MiB 限制。
3. 串行上传：首次不带 batch_id，取得编号后，后续三项携带同一个编号。
4. 每次上传成功同步 `parts/status`，保留当前批次；后续上传失败时不丢失已成功批次。
5. 四项上传完成后，显示“已暂存，尚未应用”。
6. 用户点击“校验并应用”，确认服务重启提示后 POST apply。
7. 按 applied、installed 或未知结果分别展示，随后刷新状态。

### 6.2 更新和续期

- 新一轮修改首次上传不带 batch_id，后端创建新批次并继承已有材料。
- 仅更新 CRL 时可只上传 CRL；换证书或私钥时应上传相互匹配的材料。
- 上传到 staged 的同类 part 会替换该批次该类暂存材料，其他 part 保留。
- 应用后的批次不可继续上传。不要复用 applied 的编号上传下一次更新。
- 其他管理员或浏览器已应用新配置后，旧 staged 批次可能 409；不能强行覆盖，应刷新并新建。
- 新建批次不删除旧批次；“放弃当前编辑”只清除页面状态，不调用不存在的删除接口。

### 6.3 请求并发、超时和恢复

- 同一页面上传、查询和 apply 串行处理；apply 进行中禁止重复点击、上传和切换提交对象。
- apply 会执行证书校验及服务操作，应使用独立的较长请求超时，例如 300 秒，并与网关
  超时配置协调；这不是后端承诺 300 秒内一定完成。
- apply 持有 PKI 操作锁，其执行期间状态查询也可能等待。不要一边 apply 一边高频轮询。
  响应返回或连接恢复后再查询，查询仍等待时提示处理中。
- 请求超时/连接中断不代表后端已取消。优先 GET 原 batch_id，确认后再由用户重试 apply。
- 后端允许同一已应用批次重复 apply，正常情况下直接返回 applied；前端仍不自动反复提交。
- 可按“设备地址 + 当前用户”在 sessionStorage 保存 batch_id，用于刷新后的恢复，不保存
  File、私钥、材料正文或认证令牌副本；跨设备不复用编号。
- 如果首次上传的响应丢失、前端尚未拿到 batch_id，当前没有批次列表/按文件查找接口。
  提示“首次上传结果未确认，可重新开始上传”；不要声称已找回旧批次。未应用材料不会自行生效。

## 7. curl 完整调用示例

以下为首次安装全过程。`BASE`、`SESSION_TOKEN`、`CSRF_TOKEN` 从现有环境/登录流程取得；
文件路径替换为实际测试文件。不要在日志或聊天中粘贴真实令牌和私钥正文。

```bash
BASE='https://device.example'
# SESSION_TOKEN / CSRF_TOKEN 使用现有登录接口返回值。

# 1. 查询当前材料
curl -sS "$BASE/api/cert/goose/status" \
  -H "Authorization: Bearer $SESSION_TOKEN"

# 2. 首次上传本端证书，不带 batch_id
curl -sS "$BASE/api/cert/goose/identity/import" \
  -H "Authorization: Bearer $SESSION_TOKEN" \
  -H "X-CSRF-Token: $CSRF_TOKEN" \
  -F 'file=@./enc.crt'

# 从上一步响应 data.batch_id 读取真实编号，下面只是示例值。
BATCH_ID='1234567890abcdef1234567890abcdef'

# 3. 上传本端私钥，沿用同一批次
curl -sS "$BASE/api/cert/goose/key/import" \
  -H "Authorization: Bearer $SESSION_TOKEN" \
  -H "X-CSRF-Token: $CSRF_TOKEN" \
  -F "batch_id=$BATCH_ID" -F 'file=@./enc.key'

# 4. 上传 CA 信任根
curl -sS "$BASE/api/cert/goose/ca/import" \
  -H "Authorization: Bearer $SESSION_TOKEN" \
  -H "X-CSRF-Token: $CSRF_TOKEN" \
  -F "batch_id=$BATCH_ID" -F 'file=@./goose_ca.pem'

# 5. 上传 CRL
curl -sS "$BASE/api/cert/goose/crl/import" \
  -H "Authorization: Bearer $SESSION_TOKEN" \
  -H "X-CSRF-Token: $CSRF_TOKEN" \
  -F "batch_id=$BATCH_ID" -F 'file=@./goose_crl.pem'

# 6. 查询批次，不省略 batch_id
curl -sS --get "$BASE/api/cert/goose/status" \
  -H "Authorization: Bearer $SESSION_TOKEN" \
  --data-urlencode "batch_id=$BATCH_ID"

# 7. 校验并应用；返回 503 时保留响应 JSON，按 code/data 处理
curl -sS --max-time 300 "$BASE/api/cert/goose/apply" \
  -H "Authorization: Bearer $SESSION_TOKEN" \
  -H "X-CSRF-Token: $CSRF_TOKEN" \
  -H 'Content-Type: application/json' \
  --data "{\"batch_id\":\"$BATCH_ID\"}"

# 8. 刷新当前材料
curl -sS "$BASE/api/cert/goose/status" \
  -H "Authorization: Bearer $SESSION_TOKEN"

# 若返回 GOOSE_PKI_APPLY_FAILED：用户确认重试后，重复第 7 步，仍用同一 BATCH_ID。
```

## 8. 浏览器 fetch 调用示例

下面封装保留 HTTP 状态码和错误响应 data，便于处理 503 已安装状态。项目中可改为现有
Axios/请求组件的同等实现；组件自己的超时配置、权限提示和登录恢复沿用现有机制。

```javascript
// 从现有认证模块取值，不在 GOOSE 页面另行保存令牌。
function createGoosePkiApi(baseUrl, getSessionToken, getCsrfToken) {
  const base = baseUrl.replace(/\/$/, '');

  async function request(path, options = {}) {
    const headers = new Headers(options.headers);
    headers.set('Authorization', `Bearer ${getSessionToken()}`);
    if (options.method && options.method !== 'GET') {
      headers.set('X-CSRF-Token', getCsrfToken());
    }
    const response = await fetch(`${base}${path}`, { ...options, headers });
    const body = await response.json().catch(() => null);
    if (!response.ok || !body || body.status !== 3) {
      const error = new Error(body?.message || body?.error || 'GOOSE PKI 请求失败');
      error.httpStatus = response.status;
      error.code = body?.code;
      error.data = body?.data; // 必须保留 installed/pending，不能统一丢弃错误响应。
      throw error;
    }
    return body.data;
  }

  return {
    current: () => request('/api/cert/goose/status'),
    batch: (id) => request(`/api/cert/goose/status?batch_id=${encodeURIComponent(id)}`),
    upload: (part, file, id) => {
      if (!['identity', 'key', 'ca', 'crl'].includes(part)) throw new Error('未知材料类型');
      if (!file || file.size < 1 || file.size > 1048576) throw new Error('文件须为 1 字节至 1 MiB');
      const form = new FormData();
      form.append('file', file);
      if (id) form.append('batch_id', id);
      return request(`/api/cert/goose/${part}/import`, { method: 'POST', body: form });
    },
    apply: (id) => request('/api/cert/goose/apply', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ batch_id: id })
    })
  };
}

// 页面保存 draftId；每次上传成功就更新，避免后续失败后丢失已知批次。
let draftId = null;
async function stageAll(api, files, onBatchUpdated) {
  for (const part of ['identity', 'key', 'ca', 'crl']) {
    const state = await api.upload(part, files[part], draftId);
    draftId = state.batch_id;
    onBatchUpdated(state);
  }
  // 此处只暂存。页面等待用户点击并确认“校验并应用”，不自动调用 apply。
}

async function applyConfirmedBatch(api, showState, showError) {
  if (!draftId) throw new Error('请先上传材料');
  try {
    const state = await api.apply(draftId);
    showState(state); // applied：本次应用成功；随后刷新 current 和 batch。
  } catch (error) {
    if (error.code === 'GOOSE_PKI_APPLY_FAILED' && error.data?.status === 'installed') {
      showState(error.data); // 保留同一 draftId，显示“重试应用”。
    } else {
      showError(error); // 网络/超时结果未知：恢复连接后查原批次，勿自动新建。
    }
  }
}
```

## 9. 前端验收清单

- [ ] 入口独立显示 GOOSE，原 TLS/TEE/其他模块的表单、模式参数和接口调用保持原行为。
- [ ] 四类文件各自调用正确路径，不要求 peer.crt，不使用独立 chain/import。
- [ ] 首次串行上传获得编号，后续上传、查询、应用复用同一 batch_id。
- [ ] 空文件和超过 1 MiB 的文件在提交前拦截；边界值 1 MiB 允许提交。
- [ ] 正确区分“已选择”“已暂存”“已安装待应用”“已应用”，不把上传成功显示成生效。
- [ ] 首次安装引导齐备四项；已有配置支持只更新 CRL，不将继承项误报为缺失。
- [ ] 503 GOOSE_PKI_APPLY_FAILED 显示 installed/pending，重试不重新上传或新建批次。
- [ ] apply 超时、断网或代理非 JSON 响应后，保留原编号并提供状态核对。
- [ ] 409 冲突先刷新并提示用户处理，不自动覆盖或丢弃原批次。
- [ ] 401/403/CSRF/会话锁定按现有公共机制处理；无管理员权限不能执行写操作。
- [ ] 当前安装与批次状态均可刷新；applied 不显示成实时通信健康状态。
- [ ] CRL 编号按字符串处理，过期/异常状态可见，时间包含明确时区。
- [ ] 上传/apply 不并行重复提交；应用期间不高频查询被锁定的 PKI 状态。
- [ ] 私钥正文、文件正文不出现在日志、埋点、错误上报或持久化存储中。
- [ ] 无批次列表、删除、私钥下载、实时握手状态等未实现接口的调用。
