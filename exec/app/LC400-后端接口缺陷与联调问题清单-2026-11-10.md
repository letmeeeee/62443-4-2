## 1. P0：安全中心 / 备份模块 7 个接口返回 500，页面功能整体不可用

## 2. P1：写接口未强制校验 `X-CSRF-Token`

契约（`docs/LC400-前端接口对接反馈-2026-11-06.md` 1.1）要求"写请求携带 `X-CSRF-Token`"，前端也已全部携带。实测**不携带、或携带错误值都能成功**：


| 请求                                    | 是否带 CSRF                               | 结果                                                      |
| --------------------------------------- | ----------------------------------------- | --------------------------------------------------------- |
| `POST /permission/lock` `{}`            | 不带                                      | `200 {"locked":true,"ok":true}` —— 服务端锁屏被成功触发 |
| `POST /permission/login-notice` `{...}` | 不带                                      | `200 {"ok":true,...,"version":3}` —— Banner 被改写      |
| `POST /permission/login-notice` `{...}` | `X-CSRF-Token: WRONG-TOKEN-123`（错误值） | `200 {"ok":true,...,"version":4}` —— 仍然成功           |

即：**该头缺失或错误均不拦截，校验逻辑等于没有实现**。当前防御实际只依赖 `Origin` 同源校验，一旦 Origin 白名单放宽（例如把开发机加入白名单，见 5.1）就会失去二次防护。

**期望**：所有 `POST/PUT/PATCH/DELETE`（白名单：`/permission/login`）统一校验 `X-CSRF-Token`，不匹配返回 `403 {"ok":false,"code":"CSRF_INVALID","message":"...","trace_id":"..."}`；并在审计中记录。

> 说明：本次测试因此产生了两次状态变更——`probe2` 会话被锁定后已用 `/permission/verify` 解锁；Banner 文案未改内容，但 `version` 由 1 递增到 4（见 5.6）。

## 3. P1：非标准错误契约，前端无法提示用户

### 3.1 故障录波：HTTP 200 + `code:1` + 中文 msg

```bash
GET /api/faultRecord/getRecordList?beginDt=2026-11-10&endDt=2026-11-11&pcsId=4
```

实际：

```json
{"code":1,"msg":"连接设备网络异常: pcsid=4"}
```

- HTTP 状态 **200**，无 `ok`、无 `trace_id`、无 `code`（业务错误用数字 1）。
- 前端按"成功"解析，找不到记录列表 → 录波选择框保持"请选择录波记录"，**用户看不到任何错误提示**，只会以为没有录波文件。

`pcsId=5` 同样返回 `{"code":1,"msg":"连接设备网络异常: pcsid=5"}`。

**期望**（二选一，推荐 A）：

- A：失败返回 `4xx/5xx` + `{ok:false, code:"DEVICE_UNREACHABLE", message:"连接设备网络异常", trace_id:"...", device:{pcsId:4}}`；成功返回 `{ok:true, list:[...], total:n}`。
- B：保持 200，但必须给出 `{ok:false, code, message, trace_id}` 结构，前端已按 `ok===false` 统一提示。

另请确认：`pcsid=4/5` 连接异常是设备真实离线，还是 `pcsId` 取值口径与设备表 `id` 不一致（前端传的是 `/api/device/list` 的 `id`）。

### 3.2 设备数据：缺参时泄露 Python 异常文本

```bash
# 前端未传 id（实际传 id=4）时的表现
GET /api/history/getDeviceData?beginDt=2026-11-10T00:00:00&endDt=2026-11-10T08:26:18&pageNum=1&pageSize=2
```

实际：

```json
{"code":1,"msg":"int() argument must be a string, a bytes-like object or a number, not 'NoneType'"}
```

- HTTP **200**，把 Python `TypeError` 原文返回给浏览器，属于 CR 3.7（信息泄露）。
- 参数名易混：正确参数是 `id`，前端文档曾写 `deviceId`；错误参数同时又是 200 + 异常文本，问题被完全掩盖。

**期望**：参数缺失/类型错误返回 `400 {"ok":false,"code":"INVALID_QUERY","message":"id is required","trace_id":"..."}`；任何未捕获异常统一走 500 + `INTERNAL_ERROR`，绝不把 Python 异常文本回传。

### 3.3 时间参数格式错误被当成服务器错误

```bash
GET /api/history/getFault?beginDt=2026-11-10 00:00:00&endDt=2026-11-10 23:59:59&pageNum=1&pageSize=3
```

实际：**500** `INTERNAL_ERROR`（trace `668a04a4-28d2-4c59-9338-e17c16a0407d`）。
用契约格式 `2026-11-10T00:00:00`（不带空格、不带时区）则正常返回 `{faultList:[],pageNum,pageSize,total}`。

**期望**：时间格式不合法 → `400 INVALID_QUERY` + 提示可接受的格式（`YYYY-MM-DDTHH:mm:ss`，设备本地时间，不带 Z/偏移）。当前用 500 会让监控误报"服务故障"。同类：`/api/data/*`、`/api/paraConfig/*`、`/api/upgrade/calibration`、`/api/history/getOperationlog` 缺参时是否有同样问题，建议一并回归。

## 4. P2：契约/数据质量问题

> 4.1 不再是对兼容接口的“结构缺陷”建议，已升级为**新增需求**（具名接口），完整契约见第 8 章。

### 4.1 `POST /api`（兼容寄存器）：已转为「5 个具名接口」新增需求（详见第 8 章）

> **原结论作废**：不再要求修改兼容接口的响应结构。本轮改为：后端应提供 5 个具名接口，承接前端现有 9 处 `POST /api` 调用（完整契约见第 8 章，合并自 `docs/PCS-具名接口定义与后端适配方案-2026-11-09.md`）。

**为何要替代（不是风格问题，是三个实际成本）**

1. 前端长期承担寄存器地址/位域/版本拼装知识，改一处协议就要发版前端；
2. 设备校验页 5s 轮询会产生 3 个 `POST /api` 请求，多标签页放大限流与排障成本；
3. `POST /api` 返回“文本数组 + 冒号/逗号字符串”，无法统一错误信封，没有 `trace_id`、无语义字段，不利于审计与权限细分。

**替代关系一览**（完整入参/出参/枚举/错误码见 8.3–8.7）

| 1 | `GET /api/device/pcs/verify?pcs=&groups=`  | #1 安规码、#2 关键配置（并联/并离网/运行模式）、PCS 主从机 | 已登录 1–4          |

| 3 | `GET /api/system/versions`                 | #4–#7 LC 版本与 PCS 短版本                                | 已登录 1–4          |
| 4 | `GET /api/device/pcs/charge-state?groups=` | #8 充放电状态（重启前保护）                                | 已登录 1–4          |
| 5 | `POST /api/system/time`                    | #9 写系统时间（唯一写操作）                                | 待确认 2/3/4 或 3/4  |

**统一信封**（替代原 `Registers` 文本约定）：


**兼容接口去留**：具名接口上线并稳定前保留 `POST /api`（前端有开关 `VITE_USE_NAMED_DEVICE_API`，默认走旧实现）；后端可直接在具名接口内部复用现有寄存器读取逻辑，**无需改设备侧协议**。

### 4.2 PCS 版本读取全部返回 0 → 页面显示 `V0.0`

现象（旧兼容接口实测，作为地址/数据对照证据）：


| 项       | 值                                                                                                                 |
| -------- | ------------------------------------------------------------------------------------------------------------------ |
| 请求     | `POST /api` `{"deviceid":"1,1,1,1","functioncode":"4,4,4,4","Address":"2765,3065,3365,3665","Quantity":"2,2,2,2"}` |
| 返回     | `Registers: "0,0:0,0:0,0:0,0"`（4 台全 0，前端显示 `V0.0`）                                                        |
| 地址来源 | `PCS_START_ADDRESS1=2600 + (n-1)*300 + 165`（PCS 短版本 2 字，见 8.1）                                             |

**请在实现 `GET /api/system/versions`（见 8.5）时一并确认**：

1. `pcs[].version` 是否为 0（设备侧确实未写入），还是本固件版本下 `+165` 偏移应换地址；
2. 若地址变更，请在 8.1 的寄存器常量表中给出新映射（PCS 1–4 各自起始地址与每字含义）；
3. 若设备确实无版本值，请返回 `version: null` 而不是 `"V0.0"`（前端已按 `--` 渲染空值）。

### 4.3 操作日志写入 i18n key，无法机读也无法多语言

`GET /api/history/getOperationlog?beginDt=2026-11-10 00:00:00&endDt=2026-11-10 23:59:59&pageNum=1&pageSize=2` 实际：

```json
{"operationLogList":[
  {"log_id":"26","operator":"trinastorage","operation_target":"user login",
   "operation_type":"systemMg.user.title","operation_time":"2026-11-10 08:15:49","result":1,"remark":""},
  {"log_id":"25","operator":"trinastorage","operation_target":"force logout session",
   "operation_type":"systemMg.user.title","remark":"session_id=b916...; username=trinastorage"}
]}
```

- `operation_type` 存的是**前端 i18n key**（`systemMg.user.title`，即"用户管理"的翻译键），不是稳定事件码；前端事件字典查不到就原样显示该 key。
- 同一批记录里 `operation_target` 混用 `user login` / `force logout session` / `user delete-1`，既无枚举也无对象标识规范。

**期望**：`operation_type` 使用稳定事件码（参考安全审计已采用的 `account.disable`、`account.password.reset`、`audit.export` 风格），例如 `account.login`、`session.revoke`、`account.delete`、`account.update`、`account.password.reset`；`operation_target` 放对象标识（账号名/会话 id/设备名），展示文案由前端按事件码翻译。可保留 `operation_type_text` 字段做兼容。

### 8.2 通用约定

**成功**：`{ "ok": true, "sampledAt": "2026-11-09T12:34:56+08:00", "data": { } }`（`sampledAt` 为带时区 ISO 8601）
**失败**：`{ "ok": false, "code": "...", "trace_id": "...", "message": "..." }`，前端按 `code` 本地化

**新增错误码**


| HTTP | code                             | 含义                                |
| ---- | -------------------------------- | ----------------------------------- |
| 400  | `INVALID_DEVICE_INDEX`           | `pcs`/`groups` 越界、重复或格式错误 |
| 400  | `INVALID_QUERY`                  | 其它参数错误                        |
| 400  | `SYSTEM_TIME_INVALID`            | 时间格式/范围错误                   |
| 400  | `SET_TIME_CONFIRMATION_REQUIRED` | 缺少或错误的`confirm`               |
| 403  | `FORBIDDEN`                      | 权限不足（复用）                    |
| 409  | `MAINTENANCE_IN_PROGRESS`        | 维护期间写操作被阻止（复用）        |

实现要点：拆成 `1500–1505` 六次 fc6（Quantity 必须 1）；`confirm` 缺失/错误 → 400 `SET_TIME_CONFIRMATION_REQUIRED`；格式/范围错 → 400 `SYSTEM_TIME_INVALID`；维护模式 → 409 `MAINTENANCE_IN_PROGRESS`；写失败（`error()`/`exception()`）→ 503 `DEVICE_UNAVAILABLE`；**必须写审计** `system.time.set`（`before_summary`/`after_summary` 记录旧/新时间）。

### 8.8 旧 → 新字段映射


| 旧字段/规则                              | 新字段                                                |
| ---------------------------------------- | ----------------------------------------------------- |
| `deviceid/functioncode/Address/Quantity` | 不再由前端提供，后端按`pcs/groups` 计算               |
| `Registers` 冒号/逗号文本                | 结构化数组                                            |
| 安规码 + 前端映射表                      | `standards[].code` + `standards[].name`               |
| 17060 bit9 / 17062 bit14                 | `parallelMode[].mode`                                 |
| 17064 bit5                               | `gridMode`                                            |
| 17064 bit0–4                            | `runMode`                                             |
| 12024 系列 0/1                           | `masterSlave[].role`                                  |
| 34 字数组                                | `components[].version`                                |
| LC 5 字                                  | `protocolVersion` / `softwareVersion` / `patchNumber` |
| +165 2 字                                | `pcs[].version`                                       |
| 充放电 1/2                               | `groups[].state` + `chargeDischarging`                |

### 8.9 后端实现要点

1. **读取合并**：`verify` 一次请求内完成 standards + groups + roles 三类读取；34 字版本单独接口（数据量大、刷新频率不同）。
2. **位域解析集中**：所有位移/掩码、安规码映射、版本拼装都在后端完成，前端不再持有寄存器知识。
3. **超限保护**：若内部仍用兼容读取，注意 100 组 / 每组 125 字上限；当前最大 4 台 × 34 字 = 4 组，安全。
4. **缓存**：`verify` 页 5s 轮询，建议 1–2s 合并缓存；`/api/system/versions` 可缓存 10s。
5. **失败处理**：优先整体失败 + `trace_id`；需要部分成功时按 8.3 增加 `warnings`。
6. **审计**：`POST /api/system/time` 必须写审计；读取接口只记录失败与耗时。
7. **兼容接口保留**：具名接口稳定前保留 `POST /api`，具名接口内部可复用现有寄存器读取逻辑，不改设备侧协议。
