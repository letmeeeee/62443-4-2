# PKI 管理代码检查报告

检查日期：2026-11-17。以当前工作区代码为准，包含当前 HTTPS CN 前缀规则 `LC400-`。
本轮仅检查，没有修改实现，没有操作设备服务或真实密钥。

## 检查范围与方法

覆盖通用/定制接口、Session 与管理员权限、CSR、文件私钥、共享根、CRL、批次状态、
安装/恢复日志、HTTPS 自动维护、服务应用，以及 Modbus file 后端对密钥的实际接受范围。
TEE 仅检查入口隔离，不评估 TA 内部实现。本报告不等同于标准认证评估。

在 `/tmp/pki-review-20261117/test_review.py` 编写临时复现探针；CA、证书、密钥均由
测试生成，不读取设备私钥。使用真实 OpenSSL 与本机编译的 file 身份自检程序；
systemctl/nginx 由测试替身代替。以下“复现成立”指探针观察到了不期望行为，不代表
这些行为正确。没有进行实机掉电、服务重启或远程 TLS 端口验收。

## 已复现的问题

### 1. 高：恢复日志未形成所有写入口的统一屏障

位置：`script/custom_pki.py:135`、`script/modbus_certs.py:201`、
`script/crl_store.py:185`、`script/https_certificates.py:84`。

定制入口发现 `.custom-pki/recovery.json` 会拒绝操作，但通用 CSR/身份/根操作、
正常的生效 CRL 导入和 HTTPS reconcile 没有同等检查。CRL 只有在进入“暂存根回退
验证”分支时才检查 guard，直接验证成功的导入绕过它。

复现：放置 recovery guard 后，定制查询被拒绝，通用 CSR 仍能生成；生效 CRL 仍能
写入；HTTPS reconcile 仍能成功运行，共三条探针成立。

影响：安装中断后可继续修改或应用尚未恢复的一组材料。恢复日志若随后覆盖这些文件，
会丢失恢复期间产生的变更；若日志包含 CRL，存在覆盖恢复期间新吊销记录的风险。
这项覆盖后果来自恢复代码分析，未在设备上执行破坏性验证。

建议：统一全局锁与恢复状态检查，所有写入及服务发布入口都使用；只允许只读诊断和
显式恢复绕过。定时脚本也应遵守。无需新增前端参数或接口。

### 2. 高：HTTPS prepare 会提前标记新证书已应用，后续 apply 不 reload

位置：`script/enable_https.sh:237`、`:249`。

`--prepare` 跳过 nginx 启动/reload，却仍写入 `.applied-cert.sha256` 并删除
`.reload-required`。这把“文件已准备”和“运行服务已使用”混成了同一状态。

复现：先应用旧证书，导入新证书，执行 prepare，再执行 apply；第二次 apply 成功，
但未调用 nginx reload。探针验证了服务调用序列；真实 nginx 的内存证书未实测。

影响：已有 nginx 可能继续使用旧证书，而接口显示成功。密钥泄露后的身份轮换尤其
不能接受仅凭磁盘内容判定完成。

建议：prepare 只准备配置，保留待应用标记；确认启动/reload 成功后才提交运行版本。
必要时校验监听端口实际提供的叶证书指纹。

### 3. 高：定制流程接受 RSA-PSS 私钥，file 运行后端却拒绝

位置：`script/custom_pki.py:60`、`logger/lib/modbus_identity.c:182`。

Python 检查私钥 PEM、RSA 数学有效性和公钥位数，但没有区分普通 RSA 与 RSA-PSS
密钥类型；正则也会匹配 `RSA-PSS Public-Key: (2048 bit)`。C file 后端只允许
`EVP_PKEY_RSA`，拒绝 `EVP_PKEY_RSA_PSS`。

复现：生成未加密 RSA-PSS-2048 私钥及 clientAuth 证书，定制上传、验证和安装成功
（服务回调用替身），随后真实 file 自检工具拒绝该已安装身份。

影响：控制面预检查通过却安装了运行面不支持的密钥。即使 tems 进程保持 active，
也不证明 TLS 身份可用。

建议：上传阶段严格限定普通 RSA 类型，或端到端增加 RSA-PSS 支持。应用前调用实际
运行后端做无副作用的候选身份自检，不能只依据 OpenSSL 通用解析成功。

### 4. 高：合法 CRL 更新会让 installed 批次无法重试

位置：`script/custom_pki.py:230`、`:408`、`:432`。

安装时把当前 CRL 摘要纳入 active_hashes。若服务应用失败后管理员正常更新 CRL，
该批次的后续 apply 会返回版本冲突，即使私钥、证书和根完全没变。状态同步也因
摘要不同提前返回。

复现：应用服务失败 → 正常导入 CRL → 重试原批次，返回 Conflict；再模拟旧入口已
完成服务应用并清除标记，批次仍显示 installed。

影响：服务失败后的正常恢复路径被安全数据更新阻断，批次状态可能长期与实际服务
状态不一致。

建议：将身份版本与可单调更新的吊销数据版本分开。重试时重新验证最新 CRL，不回退
CRL；仍有效则允许应用服务，已吊销则明确拒绝，并更新对应状态。

### 5. 中高（策略风险）：CRL 文件丢失会退回不检查吊销

位置：`script/pki_common.py:165`、`script/crl_store.py:252`、
`logger/lib/modbus_transport.c:160`。

当前通过文件存在与否决定是否启用 CRL，无法区分“从未启用”和“启用后意外丢失”。
Python 在文件缺失时跳过吊销验证；C 在重新创建 TLS 上下文时对 ENOENT 放行。

复现：先导入吊销某身份的 CRL，验证被拒绝；移除临时测试 CRL 文件后，同一身份
通过 Python 校验。C 分支行为由代码确认，未在此探针建立网络连接。

这符合现有“CRL 可选”的初始策略，不是普通远程用户能够直接利用的删除接口漏洞；
但升级漏文件、存储故障或管理员误删会使已启用的控制降级。

建议：持久记录 CRL 是否曾启用；启用后丢失/损坏应报告不可用并阻止新激活，不能
静默当作未配置。初次未配置时仍可保留现有兼容行为。

### 6. 中：HTTPS 与 Modbus 对过期 CRL 的运行检查策略不一致

位置：`script/https_certificates.py:53`、`logger/lib/modbus_transport.c:136`。

HTTPS check 使用 require_fresh_crl=True，并被状态查询、reconcile 和启动准备复用。
Modbus 现有运行策略则允许过期 CRL继续检查已知吊销记录，报告 stale。

复现：两种已安装身份使用同一过期 CRL，Modbus check 成功，HTTPS check 以
CRL_EXPIRED 失败。

影响：HTTPS 定时维护失败；重启时的 g3-https prepare 可能阻止 nginx 启动。
当前正运行 nginx 的证书不会仅因这次检查立即被撤下，但重启行为存在差异。

建议：明确区分“新身份激活要求新鲜 CRL”和“既有身份的运行策略”，再让查询、
续期、启动准备使用同一政策。若产品选择严格停用，也应让 UI 和文档明确表达。

### 7. 中：安全中心清单可能把实际校验不通过的身份标为 valid

位置：`routes/route_security.py:330`、`:347`。

清单分别检查链和吊销状态，但总 status 只排除 revoked，未排除 unknown。
因此缺少叶证书签发者 CRL 时，可能同时返回 status=valid、revocationStatus=unknown。
独立完整检查却会拒绝该身份。CRL_CHECK_FAILED 也缺少明确的总状态降级。

复现：有效 master 证书 + 仅覆盖另一 CA 的 CRL，清单报告 valid，而完整验证报
ISSUER_CRL_MISSING。

建议：统一健康状态归并规则，区分健康、未知、不可用和已吊销。保留现有 JSON 字段，
通过既有 status/reason 表达，不需要更改请求格式。

### 8. 中：其他身份过期时，通用入口连“仅增加根”也无法进行

位置：`script/pki_common.py:255`。

通用根导入对所有已有身份执行完整有效期和用途检查，即使新根集合完全保留旧根、
只是增加一个新根，也会因为旧身份已经过期而拒绝。

复现：生效目录放置已过期 master 证书，再导入“原根 + 新根”，得到
Shared root replacement invalidates role=master。

影响：身份过期后的 CA 迁移更难恢复；错误把原本已存在的失效状态归因于新增根。

建议：区分增量信任和撤销信任。根集合只增加时避免要求所有旧身份重新健康；移除
旧根时检查信任依赖，必要时通过完整批次迁移。仍保留新根指纹确认。

## 代码确认的诊断缺口

`routes/route_security.py:449` 捕获 Modbus 自检 stderr 却未记录，所有非零返回都
映射 PRIVATE_KEY_SELF_TEST_FAILED。此前旧二进制只支持 3072 的排错正受此影响。
建议保留返回码、后端、程序路径及经过限制/脱敏的 stderr，区分格式、位数、权限、
不匹配、算法不支持；不记录私钥内容或签名数据。

## 尚未通过实机验证的风险

- 日志/CSR/来源标记删除和 guard 删除后没有统一 fsync 目录，需掉电测试验证日志
  与数据的持久化顺序。不能把逐文件原子替换等同于整套身份掉电原子切换。
- HTTPS shell 的 configure 锁与 Python 身份锁覆盖阶段不同；校验证书之后到 nginx
  发布期间可能与其他入口交错。应以多进程测试验证最终运行指纹与提交版本一致。
- 历史 staged/备份会保存私钥，当前没有数量、空间配额、取消批次或保留期限。
  多批次并存可以保留，但应防止磁盘耗尽；无需通过自动删除所有历史来解决。
- 1 MiB 单文件上限不能代替总请求、证书数量、批次数量、锁等待及整个 apply 的时间
  上限。大量证书会触发许多 OpenSSL 子进程。部分边界可能受设备 nginx 配置限制，
  需要核对实际部署。
- systemctl is-active 只能证明进程运行，不能证明各 TLS 监听端口已加载目标身份。
  实机验收需检查 nginx 和 Modbus 对外证书、SAN 与实际握手。

## 未发现明显问题的已查边界

- `/api/cert/` 与安全中心证书接口通过全局 cert:manage 限制为权限 4；POST 沿用 CSRF。
- batch_id 为固定长度十六进制，路径没有直接拼接任意用户文件名；脚本参数使用列表，
  未发现此次路径中的 shell 拼接执行入口。
- 定制根需要完整指纹匹配；上传的 issuer chain 不会自行变成受信任根。
- 定制私钥输出及备份使用受限目录/文件权限，公开响应剔除内部密钥相关摘要。
- 新 CSR 使用既有私钥的行为与主动密钥轮换分开；定制来源标记阻止正常路径自动续签。
- 本轮没有重新引入 `/api/cert/reset`，也没有建议更改现有前端接口路径或参数格式。

这些结论仅覆盖已读代码和测试条件，不构成不存在其他问题的保证。

## 修复顺序建议

先处理恢复屏障、prepare/运行状态分离、密钥算法兼容，再处理 CRL 更新与 installed
重试、健康状态和过期策略，最后补齐配额、超时与掉电验证。
以上可以沿用现有接口，不要求新增前端请求参数。
